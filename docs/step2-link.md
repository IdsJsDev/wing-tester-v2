# Шаг 2: связь с Пито

Загрузить firmware/wing_tester/wing_tester.ino с прежними рабочими настройками Nano. Экран уже подтверждён; серво отключено, вызов его теста остаётся закомментированным.

Для классической Nano шина Wire: SDA=A4, SCL=A5. Сверить фактические провода, питание и общую землю; источник питания датчика не определять по цвету проводов.

## Поведение

Последнее уточнение интерфейса: счётчики OK/E и промежуточное «СВЯЗЬ: OK» убраны с экрана, остаются в Serial. Заголовок и спиннер остаются; причина ошибки центрируется. Вместо «Нет связи с датчиком» выводится точнее «Нет пакетов / от датчика». Пока тест нуля не реализован, после успешной связи временно показывается «Далее: тест нуля / Не добавлен»; это не итоговый успех и не выполнение этапа нуля. При добавлении этапа заменить этот экран автоматическим переходом. Крупный итоговый «ОК» предназначен только для завершения всего цикла.

Текущая конфигурация сокращена по запросу пользователя до 100 попыток: 5 блоков по 20, опрос 200 Гц, I²C 400 кГц. Упоминания 500 чтений ниже описывают предыдущую конфигурацию.

Новый интерфейс: крупный заголовок «Проверка связи...» в две строки, справа общий анимированный индикатор из точек, внизу OK/E. Анимация обновляется между блоками, не внутри измеряемого опроса. kSpinnerFrameMs задаёт период кадров; фактические обновления ограничены границами блоков. При успехе индикатор заменяется галочкой.

При провале общий renderErrorScreen() показывает крупно «БРАК» и ниже причину. Длинные причины переносятся на две строки. Если все попытки закончились неполным пакетом/тайм-аутом, причина «Нет связи с датчиком»; при частичных потерях — «Потеря пакетов». Статусы датчика и сбой расписания указываются отдельно. «БРАК» — согласованная надпись результата теста, причина может относиться к подключению или условиям проверки, а не к физической неисправности датчика. Serial сохраняет детальные счётчики и исходные пакеты. Итоговый экран появляется до последующей диагностики адресов.

Используется один кириллический шрифт 9x15; крупное слово «БРАК» рисуется четырьмя небольшими шаблонами букв, без дополнительного большого шрифта. Изображение ожидает аппаратного подтверждения.

После включения автоматически начинается «ПИТО 1: СВЯЗЬ». Не подавать поток. По умолчанию выполняются 5 блоков по 100 чтений с периодом 5000 мкс (200 Гц), I²C 400 кГц, адрес 0x28. Экран и журнал Serial обновляются между блоками; эти паузы не входят в измеряемое расписание. Номинальная сумма периодов опроса — 2,5 с, полное время больше из-за вывода.

При успехе: «СВЯЗЬ: OK», OK:500/500, 100%. Это результат только первого этапа; шум, дрейф, реакция и возврат пока не проверяются.

В обычном режиме при первой ошибке: «ТЕСТ НЕ ПРОЙДЕН» и причина. Тест заканчивается, не возобновляет чтение и сохраняет итог до Reset. В диагностическом режиме ошибки чтения накапливаются до конца проверки (см. ниже). Статус stale здесь считается провалом требования свежих чтений, а не доказательством поломки датчика. Сбой тайминга означает нарушение условий теста.

## Режим сравнения с исходным тестом

Сейчас kLinkDiagnosticMode=true: выполнить все 5×100 попыток чтения при 200 Гц/400 кГц, даже после ошибок датчика или связи. false возвращает остановку на первой ошибке. При нарушении расписания оба режима останавливаются: такой запуск нельзя считать достоверной проверкой частоты.

Экран: OK — успешные чтения, E — ошибочные; процент считается по попыткам, а не по успешным пакетам. Любая ошибка даёт итог «ТЕСТ НЕ ПРОЙДЕН»; показывается первая причина. Следующие этапы Пито после провала не запускаются. Поиск адресов выполняется только после завершения, вне счётчиков теста.

Serial дополнен first_error, diagnostic, errors, bus, timeout, stale, fault, bad_status. error — результат последней попытки, поэтому может быть 0 при итоговом провале; first_error сохраняет первую причину. FIRST_ERROR содержит первый ошибочный пакет либо incomplete. Сумма успешных чтений и ошибок равна attempts; missed — отдельный счётчик пропущенных слотов, не ошибок пакетов.

Обе конфигурации скомпилированы для Nano ATmega328P. Диагностическая: Flash 21228 байт (69%), глобальная RAM 971 байт (47%). Обычная: Flash 21316 байт (69%), глобальная RAM 991 байт (48%). Аппаратная проверка режима накопления ошибок ожидается. Проверить исправный датчик, датчик с частичными потерями и отсутствие датчика; при устойчивом расписании ожидаются 500 попыток и корректный итог по счётчикам.

## Настройки

В начале скетча: kSensorAddress, kI2cClockHz, kWireTimeoutUs, kSensorStartupMs, kSamplePeriodUs, kLinkBlocks, kLinkSamplesPerBlock, kSerialBaud. Тайм-аут должен быть меньше периода опроса. Для текущего этапа частота обновления экрана определяется границами блоков; kDisplayUpdateMs зарезервирован для последующих этапов.

## Журнал Serial

115200 бод по умолчанию. Поля LINK: state (0=выполняется, 1=успех, 2=провал), error (0=нет, 1=I²C/длина, 2=тайм-аут, 3=stale, 4=fault, 5=неверный статус, 6=тайминг), ok, attempts, missed, status, rx, raw, rawT, max_read_us. raw/rawT — последние корректные данные; при ошибке они не являются новой выборкой. status=255 означает, что полный пакет не разобран.

Разбор пакета взят из old/aspd_4525_test.ino. Справка по датчику и статусам: https://github.com/bolderflight/ms4525do/blob/main/README.md . Преобразование в давление на этом шаге не требуется; диапазон проверим перед тестом нуля.

## Проверка

- Компиляция Nano ATmega328P, AVR core 1.8.8: успешно.
- Flash 18656/30720 байт (60%), глобальные данные RAM 895/2048 байт (43%). Оставшаяся память также нужна стеку.
- На устройстве: загрузить, сообщить итог экрана. При провале сохранить строку LINK из Serial.
- После успешной проверки: выключить питание, отключить датчик и повторить запуск — ожидается остановка с причиной отсутствия данных или тайм-аута. Подключать обратно при выключенном питании.
- Аппаратные результаты пока не получены.

## Диагностика отсутствия данных

Пользователь получил «Нет данных / I2C» при наличии питания и подключении по старой схеме. Причина пока не установлена. Добавлен kDiagnoseI2cOnFailure: только после провала шины выполняется проверка ACK на рабочей частоте, поиск адресов при kDiagnosticI2cHz=100000 и отдельное чтение четырёх байт на этой частоте. Диагностика не превращает провал в успех и не изменяет результаты основного теста.

На экране появляется ACK и RX основного теста. ACK: 0=адрес подтверждён, 2=нет подтверждения адреса, 3=нет подтверждения данных, 4=другая ошибка, 5=тайм-аут. В Serial появляются DIAG, SCAN, FOUND и slow_rx. Если на медленной шине получены 4 байта, а основной тест не получает данные, исследовать частоту/тайм-аут и проводку. Если не найден ни один адрес, проверить SDA/SCL и общую землю; наличие питания само по себе не подтверждает связь.

Обновлённая диагностическая сборка: успешно, Flash 20106 байт (65%), глобальные данные RAM 949 байт (46%). Требуется загрузка и получение журнала с устройства.

Для следующей аппаратной проверки рабочая частота временно снижена с 400000 до 100000 Гц; период опроса остался 5000 мкс. Это проверка влияния частоты, а не подтверждение причины сбоя. Успешный результат на 100 кГц не подтверждает работу на 400 кГц. Старый PITOT_SERVO_TEST использует 400 кГц. Пользователь сообщил: жёлтый провод на A5, голубой на A4; назначение проверять по контактам модуля.

На 100 кГц пользователь получил «Сбой датчика» (полный пакет со статусом 3), при этом считает датчик заведомо рабочим. По его запросу текущая диагностическая конфигурация: I²C 10 кГц, опрос 10 Гц, тайм-аут 20 мс, 5 блоков по 10 чтений. Это временный медленный режим, не подтверждение целевых 200 Гц/400 кГц и не заявленный минимальный режим датчика. В LINK добавлено поле packet с четырьмя байтами в HEX; incomplete означает отсутствие полного пакета. Причина ошибочного статуса ещё не установлена; требуется результат на оборудовании.

Получен журнал: status=3, rx=4, packet=E0 06 5F 40, max_read_us=288. Обнаружена ошибка задания низкой частоты: в AVR core 1.8.8 Wire.setClock(10000) на 16 МГц записывает 792 в 8-битный TWBR (получается 24), что соответствует 250 кГц при предделителе 1. Исправлено выбором предделителя: для 10 кГц TWBR=198, предделитель=4. В журнал добавлена CLOCK с расчётной частотой (это не измерение осциллографом). Диагностика после провала теперь выполняется также для ошибочных статусов; провал не игнорируется. Подтверждение на аппаратуре ожидается.

Следующий аппаратный журнал подтвердил CLOCK calculated=10000, TWBR=198, prescaler=4; чтение 4880 мкс, rx=4, пакет E0 04 5F 20, статус 3. ACK адреса 0x28=0, тайм-аутов нет; повторное диагностическое чтение E0 06 5F 20 также содержит статус 3. Сканирование показало 0x01, 0x28, 0x29; это не доказывает наличие трёх физических устройств. Отсутствие связи больше не является текущим симптомом. Причина статуса 3 не установлена; дальнейшие проверки — полный цикл отключения питания и напряжение непосредственно на модуле. Надпись уточнена до «Статус датчика: 3», чтобы не объявлять физическую поломку установленной.

Пользователь сообщил, что датчик заработал; конкретное действие, устранившее симптом, не уточнено. По его запросу восстановлен исходный режим: опрос 200 Гц (5000 мкс), I²C 400 кГц, тайм-аут 3000 мкс, 5×100 чтений. Диагностика после провала сохранена на 10 кГц; настройка предделителя остаётся корректной для обоих режимов. Возвращённый режим ожидает подтверждения на устройстве.

## Тайм-ауты в return-v2

После изменения подтверждения выдоха пользователь сообщил «Нет пакетов от датчика». Журнал return-v2: 100 попыток, 0 успешных, error=2, first_error=2, missed=0. Это 100 тайм-аутов I²C; причина пока не установлена. Изменение выдоха не меняло конфигурацию шины и выполняется после первого этапа.

В return-v3 краткий LINK дополнен bus, timeout, status, rx. kProbeOnLinkFailure=true включает только после провала компактную проверку: ACK адреса 0x28 на рабочей частоте и чтение 4 байт при kDiagnosticI2cHz=10000. Для медленного чтения используется отдельный kDiagnosticTimeoutUs=20000: основной тайм-аут 3000 мкс меньше нормальной длительности четырёхбайтного чтения на 10 кГц. Затем рабочие настройки восстанавливаются. PROBE выводит ack, ack_timeout, slow_rx, status, read_timeout. Диагностика не меняет провал на успех, не меняет счётчики LINK и не запускает следующие этапы.

Следующий аппаратный шаг: полностью снять питание с Nano и датчика, затем повторить запуск; при сохранении ошибки получить BOOT, LINK и PROBE. Если обе проверки имеют тайм-аут, исследовать состояние шины/питание; если на медленной шине возвращаются данные, отдельно исследовать рабочую частоту и условия связи. Не объявлять физическую поломку только по этим данным.

Сборка return-v3 успешна: Flash 30596/30720 байт (99%), глобальная RAM 1124/2048 байт (54%). Это временная диагностическая сборка с очень малым запасом Flash; перед следующими дополнениями сократить диагностический код либо шрифт. Аппаратная проверка ожидается.

## Пустой экран в return-v3

Пользователь сообщил, что экран не показывает; журнал содержит два BOOT/CLOCK, но ни одного LINK. Это свидетельствует о двух запусках, однако не доказывает непрерывный автоматический сброс (загрузка, открытие Serial Monitor и ручной Reset тоже могут запускать setup). Причина пока не установлена.

В return-v4 Serial запускается до OLED, добавлены отметки INIT oled_begin/ oled_done и frame_begin/ frame_done. Serial.flush() между отметками гарантирует выдачу границы до следующего действия; все эти сообщения до измеряемого опроса. kProbeOnLinkFailure временно false, чтобы освободить Flash и изолировать текущую проверку запуска; компактные счётчики LINK и весь цикл Пито сохранены. OLED-пины и контроллер не менялись.

Сборка return-v4 успешна: Flash 29596 байт (96%), глобальная RAM 1090 байт (53%). Следующая проверка: после загрузки оставить Serial Monitor открытым, нажать Reset один раз и получить полный журнал за 10–15 секунд без дальнейших Reset. Последняя INIT поможет определить, дошло ли выполнение до рисования первого кадра. Если BOOT повторяется сам, отдельно исследовать сбросы и питание. При пустом экране после frame_done проверить контактность подключения OLED; программная причина пока не исключена.
