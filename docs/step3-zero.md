# Шаг 3: ноль, шум и дрейф

Загрузить firmware/wing_tester/wing_tester.ino. После успешных 100 чтений связи программа автоматически начинает «Проверка нуля...». Не подавать поток на протяжении обоих этапов. На экране спиннер и оставшееся время; промежуточного ОК нет.

Проверка нуля длится 10 секунд после первого вывода экрана. Опрос этого этапа 50 Гц, без исключения времени обновлений дисплея; связь по-прежнему проверяется отдельно при 200 Гц. Статистика рассчитана на 500 корректных отсчётов, 10 окон по 50 отсчётов. Окна формируются по расписанию отсчётов; пропуск полного периода или затянувшееся чтение приводят к «Сбой тайминга теста».

## Настройки в начале прошивки

| Параметр | Начальное значение | Назначение |
|---|---|---|
| kZeroTestDurationMs | 10000 мс | Длительность проверки |
| kZeroSamplePeriodUs | 20000 мкс | Период опроса, 50 Гц |
| kZeroWindowMs | 1000 мс | Окно среднего давления |
| kSensorMinPa / kSensorMaxPa | −6894,76 / +6894,76 Па | Диапазон ±1 PSI из старого теста |
| kNoiseSpanLimitPa | 30 Па | Максимальный размах отдельных отсчётов |
| kNoiseSdLimitPa | 5 Па | Максимальное стандартное отклонение |
| kDriftRangeLimitPa | 8 Па | Максимальный размах средних окон |
| kDriftSlopeLimitPaPerSec | 0,8 Па/с | Максимальный модуль наклона средних |

Пороги предварительные, не критерии производителя. Диапазон и тип преобразования A перенесены из старой прошивки; корректность для подключённой маркировки проверить до окончательного подбора порогов. Период должен укладываться в окно целое число раз, длительность должна содержать целое число окон, минимум три. Несовместимые настройки вызывают ошибку компиляции.

## Что считается провалом

- Ошибка чтения/статуса: немедленная остановка и конкретная причина, даже если диагностика связи разрешала накопление ошибок.
- Размах отсчётов выше 30 Па: «Шум датчика», остановка сразу после превышения.
- Размах средних окон выше 8 Па: «Уход нуля», проверяется начиная с трёх окон; обнаруживает также уход с последующим возвратом.
- В конце: стандартное отклонение выше 5 Па или модуль наклона выше 0,8 Па/с. Наклон определяется линейной регрессией по средним окон, в обе стороны.

При постоянном смещении, но стабильном сигнале тест может пройти: абсолютное смещение отдельно не нормировано. Ноль не подстраивается во время проверки. Только после успеха сохраняется среднее в zeroBaselinePa и устанавливается zeroReady. Это программная компенсация для следующих этапов, не калибровка самого датчика.

После успеха сейчас временный экран «Далее: тест потока / Не добавлен». Поток и возврат ещё не реализованы; итогового большого ОК пока нет. При провале остаётся общий экран БРАК с центрированной причиной до Reset.

## Проверено и следующий аппаратный шаг

Сборка Nano ATmega328P успешна: Flash 28772/30720 байт (93%), глобальная RAM 1063/2048 байт (51%). Запас Flash ограничен; перед добавлением оставшихся этапов потребуется контролировать и сокращать расход, прежде всего шрифта и диагностического кода.

Алгоритм ZeroStatistics проверен тем же AVR-компилятором через compile-time static_assert: постоянное смещение, рост 1 Па/с, падение 1 Па/с, шум без тренда и уход с возвратом к исходному значению. Тестовый файл tests/zero_statistics_test.cpp использует C++14 для вычисления проверок при компиляции; основная прошивка совместима с обычным C++11 Arduino. Эти проверки не заменяют аппаратный тест.

На устройстве выполнить запуск без потока и прислать итог и строку ZERO из Serial 115200. Поля: ready, n, windows, mean_pa, span_pa, sd_pa, drift_pa (последнее среднее минус первое), window_span_pa, slope_pa_s, baseline_pa. При ошибке чтения дополнительно ZERO_READ. baseline_pa имеет смысл только при ready=1. Поток во время проверки намеренно нарушает условия и может вызвать шум/дрейф.

## Исправление расписания экрана

Пользователь получил «Сбой тайминга теста»; журнал ZERO n=1, windows=0 подтвердил остановку после одного отсчёта нуля. Полный кадр OLED внутри sampleZero() мог занять больше периода и нарушить расписание. Обновление переработано: снимок времени/фазы один на кадр, каждая страница выводится отдельно, между страницами loop() проверяет приоритетный срок чтения. Страницу начинаем только при достаточном запасе; kZeroPageBudgetUs=10000 мкс, дополнительно учитывается измеренный максимум времени страницы с запасом 1000 мкс. Если страницы не помещаются, обновление экрана откладывается, а контроль датчика продолжается. Начальный полный кадр выводится до начала отсчёта 10 секунд.

Контроль пропусков не отключён. ZERO_TIMING показывает late_us, read_us, page_us — максимальное опоздание, длительность чтения и одной страницы. Это позволит проверить гипотезу на устройстве. Новая сборка успешна: Flash 29264 байт (95%), глобальные данные RAM 1081 байт (52%). Аппаратное подтверждение исправления ожидается. До расширения прошивки расход Flash необходимо сократить.

Пользователь прислал следующий журнал: связь 100/100 без ошибок, ZERO n=1, windows=0, но строки ZERO_TIMING нет. По этому фрагменту невозможно подтвердить загрузку версии с раздельными страницами. Добавлена метка BOOT wing-tester zero-pages-v2 и строка ZERO_FAIL reason=...; при следующей загрузке сверить BOOT и получить полный конец журнала. Не считать физическую неисправность датчика причиной ошибки расписания.

После этого пользователь подтвердил успешное прохождение теста. В версии flow-v1 успешный ноль автоматически переходит к этапу потока; прежняя заглушка «тест потока / Не добавлен» удалена. Общая ошибка чтения теперь записывается как READ, а не ZERO_READ.
